# Логика работы приложения (Вариант №22)

Документ поясняет логику каждого этапа, принятые упрощения и
сравнение с штатными инструментами Cargo.

## Этап 1. Минимальный прототип с конфигурацией

Параметры приходят из опций командной строки (`argparse`,
стандартная библиотека). После разбора выполняются три группы
проверок (секция этапа 1 в `src/main.py`):

1. Обязательные параметры: `--package`, `--version`, `--output`;
   файл вывода обязан иметь расширение `.png`.
2. Источник данных: задан ровно один из вариантов — `--repo-url`
   (реальный репозиторий) или пара `--test-mode` + `--test-repo`
   (файл тестового репозитория).
3. Значения: режим тестирования требует путь к файлу, путь требует
   режима, фильтр не может состоять из одних пробелов.

Режим `--print-config` выводит все параметры в формате
`ключ = значение` — демонстрация этапа 1.

## Этап 2. Сбор данных

Используется sparse-индекс Cargo. Запрещённые средства (cargo,
сторонние библиотеки) не применяются: запись пакета скачивается
прямым HTTP-запросом (`urllib.request`).

Правило пути пакета в индексе (`build_index_path`):

| Длина имени | Путь |
| --- | --- |
| 1 символ | `1/{имя}` |
| 2 символа | `2/{имя}` |
| 3 символа | `3/{первая буква}/{имя}` |
| 4 и более | `{2 буквы}/{следующие 2}/{имя}` |

Например, `serde` -> `https://index.crates.io/se/rd/serde`.

Файл записи — JSON Lines: одна строка = одна версия. Выбирается
строка с заданной версией (`select_version`), из поля `deps`
берутся зависимости с `kind` = `null` или `normal` (dev- и
build-зависимости и optional-зависимости не считаются прямыми).
Режим `--direct-deps` печатает их список — демонстрация этапа 2.

## Этап 3. Основные операции

Граф строится алгоритмом DFS **без рекурсии** — явный стек
(`walk`):

1. Корень помечается как «в работе», его зависимости кладутся на стек.
2. Вершина с вершины стека снимается, помечается, её соседи
   кладутся на стек.
3. Пакеты, чьё имя содержит подстроку `--filter`, не кладутся на
   стек — вся их подветка исключается из анализа.
4. Сосед «в работе» (серый) — ребро цикла: обход в него не идёт,
   поэтому зацикливание невозможно. Итоговые циклы дополнительно
   перечисляются в предупреждениях (`find_cycles`, тоже без рекурсии).

Тестовый режим читает файл формата `ПАКЕТ : ЗАВИС1, ЗАВИС2`
(пакеты — большие латинские буквы). Тест на цепочке из 3000 узлов
доказывает отсутствие рекурсии.

## Этап 4. Дополнительные операции

Порядок загрузки (`get_load_order`) — пост-порядок
итеративного DFS: зависимость всегда загружается раньше
использующего её пакета. Циклы не приводят к зависанию.

### Сравнение с реальным менеджером пакетов

Cargo не печатает «порядок загрузки» напрямую; ближайшие штатные
инструменты — `cargo tree` (дерево зависимостей) и порядок
компиляции `cargo build -v`. Ниже — процедура сравнения и
фактические результаты, полученные на cargo 1.99.0 (стабильный
Rust, Windows, Git Bash), пакет `serde 1.0.210`.

#### Процедура сравнения (этап 4.1)

```bash
# 1. Наш порядок загрузки:
python src/main.py --package serde --version 1.0.210 \
  --repo-url https://index.crates.io --output serde.png --load-order

# 2. Реальный менеджер: создать тестовый проект и добавить пакет.
#    Фича derive нужна, чтобы включить опциональную зависимость
#    serde_derive (наш инструмент берёт полный normal-список
#    зависимостей записи индекса и не различает фичи):
cargo new cargo-demo && cd cargo-demo
cargo add serde@1.0.210 --features derive

# 3. Дерево зависимостей (штатный инструмент):
cargo tree -e normal

# 4. Фактический порядок компиляции (cargo строит зависимости
#    раньше использующих их пакетов):
cargo build -v 2>&1 | grep Compiling
```

Примечание: `cargo add serde` без версии заберёт новейшую
совместимую версию (1.0.229 на момент проверки), а у serde
>= 1.0.220 появляется дополнительная зависимость `serde_core`,
поэтому для сравнения графа с нашим инструментом версию нужно
фиксировать (`serde@1.0.210`).

#### Фактические результаты для `serde 1.0.210` (cargo 1.99.0)

Наш вывод (`--load-order`; корень `serde` в список не включается,
он загружается последним — после всех своих зависимостей):

```text
Порядок загрузки зависимостей:
  unicode-ident
  proc-macro2
  quote
  syn
  serde_derive
Пакетов в графе: 6
```

`cargo tree -e normal`:

```text
cargo-demo v0.1.0 (C:\...\cargo-demo)
└── serde v1.0.210
    └── serde_derive v1.0.210 (proc-macro)
        ├── proc-macro2 v1.0.107
        │   └── unicode-ident v1.0.26
        ├── quote v1.0.47
        │   └── proc-macro2 v1.0.107 (*)
        └── syn v2.0.119
            ├── proc-macro2 v1.0.107 (*)
            ├── quote v1.0.47 (*)
            └── unicode-ident v1.0.26
```

`cargo build -v 2>&1 | grep Compiling`:

```text
   Compiling proc-macro2 v1.0.107
   Compiling quote v1.0.47
   Compiling unicode-ident v1.0.26
   Compiling serde v1.0.210
   Compiling syn v2.0.119
   Compiling serde_derive v1.0.210
   Compiling cargo-demo v0.1.0
```

Выводы сравнения:

- Состав графа совпадает: `serde` -> `serde_derive` ->
  (`proc-macro2`, `quote`, `syn`), плюс `unicode-ident` — 6
  пакетов у обоих инструментов.
- Порядок компиляции у cargo — та же топология, что и наш
  пост-порядок: зависимость всегда раньше использующего её
  пакета (`unicode-ident` -> `proc-macro2` -> `quote` -> `syn`
  -> `serde_derive`), корневой крейт компилируется последним.
  Строки `unicode-ident`, `quote` и `serde` в выводе cargo
  «выбиваются» только из-за параллельной сборки (см. п. 3).

#### Объяснение возможных расхождений

1. **Версии транзитивных зависимостей.** Cargo разрешает версии
   по semver-ограничениям (`req`) всего дерева и допускает
   несколько версий одного пакета (`foo v1`, `foo v2`). Наш
   инструмент для транзитивных узлов берёт **новейшую** версию
   из индекса (осознанное упрощение), поэтому показывает один
   узел.
2. **Фичи и платформы.** Cargo учитывает target-specific
   зависимости и включённые фичи; наш инструмент берёт полный
   normal-список зависимостей записи индекса. Реальный пример:
   `serde_derive` — опциональная зависимость serde, включаемая
   фичей `derive`; без `--features derive` в тестовом проекте
   `cargo tree` показывает только `serde`, а наш инструмент —
   полный граф вместе с `serde_derive`.
3. **Параллелизм.** `cargo build` при нескольких потоках
   компилирует независимые пакеты одновременно, поэтому порядок
   строк в его выводе недетерминирован; сравнивать нужно
   множество и топологию, а не буквальный порядок строк.
4. **Циклы.** В реальном Cargo зависимости пакетов ацикличны
   (циклы возможны только через dev-зависимости); наш инструмент
   дополнительно корректно обрабатывает циклы в тестовом режиме.

## Этап 5. Визуализация

1. Текст PlantUML: `build_plantuml` формирует
   `@startuml ... [A] --> [B] ... @enduml`; файл `<имя>.puml`.
2. PNG: собственный кодировщик собирает чанки
   IHDR/IDAT/IEND (zlib, struct); холст и компоновка — в том же
   `src/main.py`: узлы раскладываются по уровням BFS
   от корня, подписи — собственный шрифт 5x7, рёбра — стрелки
   Брезенхема с наконечниками.
3. Примеры для трёх пакетов: `A` (тестовый репозиторий), `serde`,
   `clap` (реальный индекс) — команды в README.
4. Сравнение со штатными средствами визуализации: у Cargo нет
   встроенной графической утилиты; штатный текстовый инструмент —
   `cargo tree` (дерево сверху вниз, узлы повторяются для разных
   версий, включает dev/build-зависимости по флагам). Наша
   диаграмма — направленный граф без дубликатов версий, только
   normal-зависимости. Основные ожидаемые расхождения — дубликаты
   версий и target-specific зависимости (см. этап 4).
